      4.1. 基本流程

      4.1.1. 网站三大件

      • 域名（用于访问网页）：购买
      • 服务器（用于托管静态网站）：　Github可以免费托管静态网站，当作服务器用；Github pages、Vercel、Readthedocs 托管静态网页
      • 网站程序（网站内容）：Hugo……，

      4.1.2. 网站分类

      • 静态网站

        • 指存放在服务器文件系统中实实在在的HTML文件。访问URL时，浏览器下载HTML，渲染后呈现在窗口中
        • JavaScript 发展出了拥有后端服务器功能的 Node.js。
          • 相比传统的后端语言，Node.js 拥有超强的性能和响应速度，能够轻松处理大量请求和高并发。
        • 静态网站生成器 SSG (Static Site Generation)
          • 静态场景，比如官网、博客、文档等，不需要频繁更新，造成浪费
          • SSG预先生成静态HTML网页，托管到服务器即可显示
          • SSG工具：
            • 静态网站生成比较
            • 博客：Hexo、Hugo、Jekyll、NotionNext、Sphinx
              • Hugo: 有现成的主题，直接用
            • 文档程序：VuePress、VitePress、Docusauru、Docsify 、Astro、GitBook、MkDocs、Gridsome、Pelican
        • 托管静态网页
          • 方案
            • 参考：托管静态网站
            • Github pages、Vercel、Readthedocs、CloudFlare Pages
            • Cloudflare Pages：高级、更快、与 Git 仓库的自动整合、全球 CDN 支持、无限制流量（在免费方案内）等
          • 如何选择
            • 目标用途：如果只是展示型页面或小型博客，Tiiny Host 简单便捷；要持续部署更新、使用 Git 的话，Render／Netlify／Vercel 更适合。
            • 流量与带宽预估：如果预计访问量大，带宽或存储大，则选择带限额较高的平台（如 Kinsta）或将来考虑付费升级。
            • 技术栈需求：如果使用前端框架或需要自动构建流程，则优先选择支持构建、自动更新的平台。
            • 自定义域名与 SSL：确认免费方案是否支持自定义域名 + HTTPS，这对品牌与 SEO 很重要。
            • 后续扩展能力：开始免费是没问题，但如果后期可能加入动态功能或大流量访问，提前了解升级路径也很重要。

      • 动态网站：

        • 根据当前时间环境参数、数据库，动态生成HTML
        • 不直接写 HTML（直接翻译成网页内容的代码），而是前端后端结合
        • 前端：JavaScript
        • 后端：PHP、Java、Python，通过数据库动态展示网页；发展出了Windows Server，还有 Linux 下 LNMP、LAMP、LNMT 的服务器生态。

      4.1.3. 个人博客方案

      • 本质上是，本地写文档内容，通过Github同步管理，Sphinx/Hugo工具生成静态网页（SSG），再用服务器托管网页

      • 方案：

          1. 文档编辑：markdown，reStructuredText for Sphinx, Github 存储同步；编辑内容
          1. 静态网站生成工具: Sphinx; Hugo; 编辑主题
          1. 搭载平台：Github pages; CloudFlare Pages; Readthedocs; Gitbook
        • 比较
          • Gitbook：主题死板，不灵活
          • Readthedocs + Sphinx：需要reStructuredText语法，文档标题需要为md文件内部一级标题？编号？
          • Hugo

      • 方案 教程

        • Hugo + Vercel
        • Github pages：用户名.github.io；
        • Astro + github pages
        • 🎯 Github + Sphinx + Readthedocs
        • 🎯 Github + Hugo/Sphinx + CloudFlare Pages/Github pages

      • 自动更新Github Actions

        • 流程图 
          •       flowchart LR
        A(文档更改) --提交--> B(main分支) --Actions--> C("编译，产生html，提交到docs分支") --> E("RTD自动编译，更新文档")
        • 设置GitHub actions 配置文件.github\workflows\xxx.yml
          • 功能：每当main分支改变时执行，将新文档push到docs分支；
          •   name: RTD

  on:
    push:
      branches: [ main ]
      paths:  # 当更改以下文件时，会触发Actions更新文档
        - 'sphinx_readthedocs_test/**'
        - '.github/workflows/Readthedocs.yml'
        - 'README.md'

  env:
    REPO_HTTPS: https://github.com/Phoenix0qi/sphinx_readthedocs_test.git
    CLONE_URL: ${{ github.event.repository.clone_url }}
    USER_NAME: ${{ github.event.repository.owner.name }}
    USER_EMAIL: ${{ github.event.repository.owner.email }}
    SUBMMIT_BRANCH: docs
    PACKAGE_NAME: sphinx_readthedocs_test

  jobs:
    Deploy_TO_RTD:
      runs-on: ubuntu-latest

      steps:
        - uses: actions/checkout@v4

        - name: Set up Python 3.12
          uses: actions/setup-python@v4
          with:
            python-version: '3.12.0'
            architecture: 'x64'

        - name: Prepare docs directory
          run: |
            mkdir -p docs_build
            # cp -r your_package docs_build/ || true
            cp -r source docs_build/source || true
            cp README.md docs_build/ || true
            cp .readthedocs.yaml docs_build/ || true
            cp requirements.txt docs_build/ || true

        - name: Setup git config
          run: |
            git config --global user.email "github-actions[bot]@users.noreply.github.com"
            git config --global user.name "github-actions[bot]"

        - name: Push to docs branch
          run: |
            cd docs_build
            git init
            git remote add origin https://x-access-token:${{ secrets.GITHUB_TOKEN }}@github.com/${{ github.repository }}.git
            git checkout -B docs
            git add .
            git commit -m "Update docs from main $(date)"
            git push -f origin docs

    ├── _index.md // <- /blog/

              • Hextra 有三种content格式
                • docs、blog、default
                • 格式
                  Layout Directory Features
                  docs content/docs/ Ideal for structured documentation, same as this section.
                  blog content/blog/ For blog postings, with both listing and detailed article views.
                  default All other directories Single-page article view without sidebar.
                • docs 
                  •   ---
  title: My Docs
  cascade:
    type: docs
  ---
                  • The above example configuration ensures that the content files inside content/my-docs/ will be treated as documentation (docs type) by default.
